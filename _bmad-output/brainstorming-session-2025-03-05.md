## Brainstorming Approach

**Selected Mode:** YOLO (full technique pass, facilitator-driven)

**Business premise (user-provided):**
- Simple shooter: one core loop — **dodge, shoot, collect** (repeat).
- Rewards: **brand voucher/coupons** + **free data** (real-world value).
- Difficulty scales with **data pack value** — higher value pack = harder run; winning feels proportional to reward.
- Vouchers = **collectibles** (in-game collectibles map to real vouchers).
- MVP scope; build on this foundation.

**Techniques in use:** MDA, Core Loop, Player Fantasy, Constraint Box, Reward Schedule, Progression Curve, Genre Mashup (shooter + rewards platform), Verbs Before Nouns (dodge, shoot, collect).

**Focus areas:** Core loop clarity, difficulty–reward alignment, voucher/data as collectibles, one-finger controls, retention, fairness, brand integration.

## Ideas Generated

*Generated in YOLO pass — building on business premise.*

**[Category 1]**: Value-Gated Runs  
_Core Loop_: Player picks a "data pack tier" before the run (e.g. 100MB / 500MB / 1GB). Run difficulty and enemy density scale with that tier. Dodge, shoot, collect vouchers mid-run; at the end, survive to claim the data pack. One finger: drag to move, auto-shoot or tap to shoot.  
_Novelty_: The stake is chosen upfront — risk/reward is explicit and tied to real-world value, not just score.

**[Category 2]**: Voucher Stream as Collectibles  
_Core Loop_: Vertical scroll; enemies drop voucher fragments or full vouchers. Collectibles float in lanes — dodge obstacles, shoot enemies, collect vouchers. Vouchers are "cards" (brand, category, rarity); collecting a set unlocks redemption.  
_Novelty_: Collectibles are real offers; completionist urge drives both play and redemption.

**[Category 3]**: Data Pack as Boss / End Gate  
_Core Loop_: Standard dodge/shoot/collect. The "level" is time- or wave-based. Final wave or "gate" is harder; winning unlocks the data pack for that run. Difficulty of the gate matches pack value.  
_Novelty_: Data pack isn’t a random drop — it’s the clear end goal of every run, so difficulty feels fair and intentional.

**[Category 4]**: One Finger, Three Verbs  
_Core Loop_: Single finger: hold/drag = move ship (dodge), release/tap = shoot (or auto-shoot), passing through glowing pickups = collect. No separate "collect" button — collection is movement-based.  
_Novelty_: Hypercasual clarity; all actions map to one input channel, reducing cognitive load and fitting rewards-focused play.

**[Category 5]**: Seamless Difficulty Ramp (No Visible Slider)  
_Core Loop_: Player doesn’t choose "hard mode." They choose reward tier (data pack size/value). Back-end scales bullet speed, spawn rate, and lane density so higher-value runs are objectively harder. Same mechanics, different numbers.  
_Novelty_: Difficulty is invisible but fair; players self-select by appetite for reward.

**[Category 6]**: Voucher Lanes vs Danger Lanes  
_Core Loop_: Vertical scroll with lanes. Some lanes have voucher pickups, others enemies/obstacles. Player weaves to collect vouchers while dodging and shooting. Risk = going into a voucher lane when enemies are there.  
_Novelty_: Spatial risk/reward; vouchers as collectibles create meaningful lane choices.

**[Category 7]**: Brand "Seasons" or Rotating Pools  
_Core Loop_: Same dodge/shoot/collect. Voucher pool is tied to brands/partners — e.g. "Food week," "Tech week." Collectibles and maybe end-screen offers rotate; keeps content fresh and supports commercial deals.  
_Novelty_: Gameplay loop is stable; only the rewards and visuals rotate, which suits brand campaigns.

**[Category 8]**: Free Data as the "Big Win"  
_Core Loop_: Small wins = vouchers (frequent). Big win = data pack (complete a harder run or a set of runs). Data pack value amps with difficulty so "free data" is the aspirational reward that justifies the ramp.  
_Novelty_: Clear hierarchy — vouchers for consistency, data for commitment/skill — without changing the core loop.

**[Category 9]**: Run Length = Session Control  
_Core Loop_: Short runs (1–3 min) so one session = one attempt at a chosen data pack. Fail = no pack, try again. Win = pack + vouchers collected. Session boundary is clear for both player and ads/offers.  
_Novelty_: Aligns with hypercasual and rewards platform: short, repeatable, easy to monetize and measure.

**[Category 10]**: Vouchers as Shield / Power-Up  
_Core Loop_: Collecting a voucher type (e.g. "Brand A") can grant a short shield or burst shot. Redemption is separate (post-run). In-run, vouchers double as collectible + micro power-up to create moment-to-moment variety.  
_Novelty_: Collectibles affect gameplay without complicating the one-finger loop; brands get in-run visibility.

**[Category 11]**: Tiered End Screen  
_Core Loop_: After run: "You earned: Data pack (500MB) + 3 vouchers." Show voucher cards and data amount. Option to "Play again for 1GB" or "Claim and exit." Clear cause (difficulty chosen) and effect (rewards).  
_Novelty_: Transparency builds trust; upsell to higher tier is natural and non-pushy.

**[Category 12]**: Anti-Grind Fairness  
_Core Loop_: Same as value-gated runs. To avoid exploit: limit wins per day per tier, or scale difficulty with recent wins. High-value packs stay "hard" so only real skill/session investment pays.  
_Novelty_: Protects both business (sustainable data/voucher cost) and player (fair, not pay-to-easy).

**[Category 13]**: First-Win-of-the-Day Bonus  
_Core Loop_: First successful run of the day gives a bonus voucher or a small data top-up. Encourages daily open; rest of day is standard dodge/shoot/collect for chosen tier.  
_Novelty_: Retention hook without changing core loop; fits "rewards app" habits.

**[Category 14]**: Collectible Sets for Redemption  
_Core Loop_: Vouchers come in sets (e.g. "Collect 3 food vouchers to unlock combo"). Player collects during runs; completing a set unlocks a better redemption or extra data.  
_Novelty_: Collectibles have structure; gives goals beyond "just survive" and supports brand bundles.

**[Category 15]**: Minimal UI, Maximum Clarity  
_Core Loop_: HUD: ship, bullets, pickups, maybe a "data pack progress" or "distance to gate." No score unless it feeds reward logic. End screen = rewards only.  
_Novelty_: Reinforces that the game is about earning, not leaderboards — good for non-gamer rewards users.

## Themes and Patterns

- **Difficulty–reward coupling**: Every idea assumes higher value = harder run, with no fake difficulty.
- **One loop, many reward layers**: Dodge, shoot, collect stay constant; vouchers vs data vs tiers add structure.
- **Vouchers as dual-purpose**: Collectible (collection urge, sets) and optionally gameplay (power-up, lanes).
- **Session = one run**: Short runs keep sessions clean and match hypercasual + rewards use cases.
- **Brand integration**: Rotating pools, voucher sets, and end-screen clarity support commercial use.
- **Trust and fairness**: Transparent stakes, anti-grind, clear cause–effect so players accept difficulty.

## Promising Combinations

- **Value-Gated Runs + Data Pack as Boss + Tiered End Screen** — Full loop: choose tier → play scaled run → reach "gate" → win pack + vouchers → clear end screen. MVP-friendly and easy to explain.
- **Voucher Lanes + One Finger Three Verbs** — Simple control, spatial risk/reward; vouchers as collectibles drive lane choice and feel like "grabbing rewards."
- **Brand Seasons + Collectible Sets** — Rotating voucher pools and set completion support campaigns and give players repeat goals without changing mechanics.
- **Seamless Difficulty Ramp + Anti-Grind** — Back-end scaling keeps difficulty fair; caps or cooldowns keep rewards sustainable and credible.

## Refinements: 3 Tries, End Boss, Free-Data Seekers

*User additions: 3 tries per level, different boss at end with difficulty scaling, and experience for people who mainly want free data.*

### 3 tries for all levels

- **Structure:** Each run/level gives the player **3 lives/tries**. Use all 3 → run over, no pack (can start a new run). Win before losing 3 → claim data pack + vouchers.
- **Why it helps:** Softens the binary “one shot” feel without breaking session control. Still one run = one session; the run just has 3 attempts inside it. Good for “I’m here for the data but I’m not great at shooters.”
- **Design note:** Keep run length fixed (e.g. same total time or same number of waves); 3 tries only affect how many “deaths” you get before fail. Avoid making runs longer just because of extra lives.

### Different boss at end; boss difficulty amps with tier

- **Structure:** Every run ends with a **boss fight**. Different bosses (e.g. by tier or rotation) so it’s not the same encounter every time. Boss difficulty scales with **data pack tier** — higher tier = harder boss (more health, faster, more patterns).
- **Why it helps:** Clear “final gate” before the reward; boss = memorable moment and clear difficulty signal. Variety (different bosses) reduces repetition; scaling with tier keeps fairness (bigger reward = harder boss).
- **MVP:** Start with 2–3 boss variants; difficulty params (health, speed, bullet density) are tier-driven. Same run structure: waves → boss → win/fail → rewards.

### People who are mainly coming for free data

- **Segment:** Users whose primary goal is “get free data” with minimal interest in the game itself. They’ll tolerate gameplay if it’s short and fair; they’ll drop if it feels like a grind or a paywall.
- **Options:**

| Approach | What it looks like | Pros | Cons |
|--------|--------------------|------|------|
| **Same loop, lowest tier only** | They always pick 100MB (easiest). Same game, minimal difficulty. | One product, fair. | Still need to play; some will churn. |
| **Guaranteed small data per run** | Every completed run (even “easy” tier) gives a small data amount; big packs stay hard. | “I always get something” reduces frustration. | Risk of devaluing higher tiers if small is “enough.” |
| **Short “data-only” run** | Optional 30–60 sec “quick run” or “data run”: fewer waves, easier or no boss, fixed small data reward. | Low friction for data seekers. | Two run types to balance and explain. |
| **Tutorial / first-run bonus** | First run of the day or first ever is easier or has a guaranteed small pack so data seekers get an early win. | Onboards and rewards quickly. | Need to avoid abuse (e.g. multi-account). |

- **Recommendation:** Start with **same loop, tiered difficulty** and a **lowest tier** that is genuinely easy (and maybe capped daily so it’s “free data for light engagement”). Add a “quick data run” or guaranteed-small-data only if data shows a big segment failing or dropping at the boss. Keep one run = one session so analytics and rewards stay simple.

## Engine: Multiple Core Loops

**Concept:** An engine (platform) that keeps the **rewards layer** fixed (vouchers, data packs, difficulty–value coupling, redemption, anti-grind) and lets **multiple core loops** plug in. Same business model; different games or modes.

**Why it helps:** One integration for brands/telcos; multiple games to retain different players, A/B test loops, or roll out new genres without rebuilding rewards and fairness.

**What the engine owns (shared):**
- Reward catalog: data pack tiers, voucher pools, sets, brand rotations.
- Difficulty–value mapping and anti-grind (caps, cooldowns).
- Session outcome: win/fail, payload (vouchers + data), end screen, claim flow.
- User identity, progress, and redemption (so collectibles and data persist across loops).

**What each “loop” owns (per game/mode):**
- Core verbs (e.g. dodge, shoot, collect vs. merge, tap, match vs. run, jump, collect).
- Level/wave/run structure and difficulty curve *parameters* (the engine still maps “tier” → difficulty).
- Controls and feel (one-finger, two-finger, etc.).
- In-run collectible placement (vouchers as pickups, sets, or power-ups).

**Variants:**

1. **Single app, multiple games** — One app, main menu: “Shooter,” “Runner,” “Puzzle.” Each is a different core loop; same wallet, same voucher/data rewards and tier rules.
2. **Single app, one loop at a time (swappable)** — Ship shooter first; later add “Runner mode” or “Puzzle mode” as alternate entry points. Engine is built once; new loops are new game modules.
3. **Config-driven loops** — Same codebase, different configs: e.g. “shooter” config (bullets, lanes, collectibles) vs “runner” config (obstacles, jump, collectibles). One engine, many configs; minimal new code per loop.
4. **Template + hooks** — Engine defines a “loop template”: e.g. (pick tier → play run → reach end condition → resolve win/fail → grant rewards). Each game implements: run simulation, end condition, and what “collect” means. Redemption and difficulty logic stay in the engine.

**MVP path:** Ship one loop (e.g. shooter) with rewards and difficulty–value coupling. Design APIs/contracts so “run result” (tier, win/fail, collectibles earned) is the only thing the engine needs. When adding a second loop, it just implements the same contract; engine stays unchanged.

## Party Mode: Perspectives on Category 9 (Run Length = Session Control)

**Topic:** The team discussed **Category 9 — Run Length = Session Control**: short runs (1–3 min), one session = one attempt at a chosen data pack; fail = no pack / try again; win = pack + vouchers collected. Session boundary is clear for both player and ads/offers.

**Agents invited:** Samus Shepard (Game Designer), John (Product Manager), Mary (Business Analyst).

---

### Samus Shepard (Game Designer)

Session control here is doing a lot of heavy lifting. One run = one session means the player always has a clear mental model: "I'm playing for this one outcome." No mid-run save, no "I'll come back later" — you either win and get the pack + vouchers or you don't. That's *perfect* for the fantasy you're selling: "I'm risking one shot at the 1GB pack." The run length (1–3 min) keeps the stakes from feeling like a grind. If it were 10 minutes, losing would feel punishing; at 90 seconds, it's "one more try" territory. So from a *feel* perspective: lock the run length tight, make the end state binary (win = rewards, fail = try again), and keep the HUD minimal so the only thing that matters is "am I going to make it?" That clarity *is* the session control — the game doesn't need to say "session over"; the run *is* the session. Let's GOOO — this is the right lever for hypercasual + rewards.

---

### John (Product Manager)

Why does session length matter? Because it defines the *job* the product does. If the job is "kill 2 minutes and maybe get something useful," then 1–3 min runs are the right unit. If the job is "earn my data/vouchers with minimal friction," then the same run length keeps the value exchange obvious: one attempt, one outcome, one claim. The risk is making runs too long — then you get "I'll finish later" and drop-off, or "that was too much for a voucher" and perceived unfairness. So the product requirement is: **run length is a fixed design constant** (e.g. 90 sec or 2 min), not a tunable. That way ads/offers and reward logic can assume "one run = one session" in their models. Ship the smallest thing that validates: can we get users to complete runs at that length and come back for another? If yes, session control is doing its job.

---

### Mary (Business Analyst)

From a market and rewards-platform lens: session control is your *measurement* and *monetization* boundary. Rewards apps and telco promos need a clean unit of engagement — "one completed run" is that unit. Ad integrations, brand voucher drops, and data-pack fulfillment all map cleanly when the session is bounded: one run, one result, one payload. Competitive pattern: many hypercasual games use "one level = one session" or "one life = one session"; you're aligning with that so retention and LTV metrics (sessions per day, runs per user) are comparable. The insight is that *short* runs (1–3 min) also reduce support and fraud surface — "I didn't get my pack" has a clear referent (that run, that tier). So session control isn't just design; it's the boundary for analytics, partner reporting, and fairness. Document it as a product pillar: "One run = one session. Session length is fixed and short."

---

### Summary (Facilitator)

- **Samus:** Run length and binary win/fail create clear player psychology and "one more try"; keep runs short and HUD minimal.
- **John:** Run length should be a fixed design constant so the product job ("kill 2 min / earn rewards") and validation are clear.
- **Mary:** One run = one session is the right unit for measurement, ads, partners, and support; short runs reduce ambiguity and fraud.

**Recommendation:** Treat "Run Length = Session Control" as a non-negotiable pillar: fix run length (e.g. 90 sec or 2 min), one attempt per run, one outcome (pack + vouchers or try again). Design, product, and business all align on that boundary.
